# CE-QUAL-W2 v2026.10

This version applies the corrections from the October 2026 review of the gfortran port of CE-QUAL-W2 v4.5 (Intel Fortran on Windows to gfortran on macOS and Linux) to v2026.02. The hydrodynamic and water-quality computations are unchanged: on the verification models, v2026.10 reproduces the water levels, velocities, temperatures, dissolved oxygen and all other constituents of v2026.02 built with the same compiler and flags, exactly, at every output time. The changes are in how a run reports failure, the kinetic-flux output, the build, the status file, and three code paths that the verification models do not use.

## Changes

- **A run that stops on an error now reports failure** (`w2_4_unix.f90:51-55, 395, 1670-1677, 1696-1713`). In v2026.02 the driver set its result to 1 before the time loop and never changed it, so every run, finished or failed, printed "CE-QUAL-W2 ended with status code: 1" and ended with process exit status 0; a run stopped by an error (for example "Unstable water surface elevation", written to `w2.err`) also printed "Simulation completed." and left `w2_status.json` at "running". Now a run that stops on an error prints the Julian day and the error message, copies the first lines of `w2.err` to the console, writes one line to standard error, writes status "failed" to `w2_status.json`, and ends with exit status 1. A run that reaches TMEND prints "CE-QUAL-W2 completed successfully." and ends with exit status 0. Errors before the time loop (run directory or control file not found, invalid `w2_multiple_WB.npt`) also end with exit status 1 (`w2_4_unix.f90:110, 115, 175, 231, 241, 247`); they used STOP, which gives exit status 0. The exit uses the GNU `EXIT(1)` intrinsic rather than `ERROR STOP`, because with `-fbacktrace` gfortran 16 prints a backtrace after `ERROR STOP`, which reads as a crash of the program itself.
- **Kinetic-flux output corrected for layer addition** (`layeraddsub.F90:353`, `outputa2w2tools.F90:980-981`). When a layer was added, the accumulated mass of every kinetic-flux term in the old surface cell was copied into the new surface cell but kept in the old one as well, except where the new layer reached the segment bottom; layer subtraction then merged the two, so each addition counted the surface cell's accumulated mass twice. The reset after each flux output also skipped the inactive upstream segments of the first branch, so their sums were reported again when the segments were re-added. Flux values in `kflux_wb*.csv` and `flx*.opt` were inflated in every output interval with layer additions; the oxygen sink and every other source and sink applied to the model state were not affected. The accumulator of the old surface cell is now zeroed after the copy, and the reset covers the whole waterbody.
- **Release and compiler recorded** (`preprocessor_definitions.fpp:8-10`, `w2_4_unix.f90:34, 140-144`). The console banner and `W2CodeCompilerVersion.opt` now give the release (v2026.10), and `W2CodeCompilerVersion.opt` records the compiler version and the full compiler options. W2VER stays 4.5: it is the CE-QUAL-W2 model version written into output headers.
- **Fortran runtime linked statically** (`Makefile:47-50`). v2026.02 executables load `libgfortran` and `libquadmath` from `/opt/homebrew/opt/gcc/lib/gcc/current` at run time, so a Homebrew GCC upgrade changes the runtime of an existing executable. v2026.10 links them statically; `otool -L ce-qual-w2` lists only `/usr/lib/libSystem.B.dylib`.
- **Optional floating-point exception trapping** (`Makefile:52-62`): `make FPE_TRAP=1` adds `-ffpe-trap=invalid,zero,overflow`, which stops a run at the first invalid operation, division by zero or overflow, as the Intel Release build does with `/fpe:0`. It is off by default. On Apple Silicon the trap arrives as SIGILL (exit status 132); the gfortran backtrace names the routine, but its line number can be that of the last call before the trapping instruction, so the Makefile gives the lldb command that reports the exact line.
- **Heat exchange: BCONV defined for every CFW** (`heat-exchange.f90:76-82`). The wind-function conversion BCONV was set only for CFW = 1 or 2 and was otherwise an undefined local (zero under `-finit-local-zero`). The two coded constants are kept; any other CFW now uses the general conversion `W_M2_TO_BTU_FT2_DAY / MPS_TO_MPH**CFW`, which reproduces the coded constants to within 0.02 percent (3.400753 against 3.401062 for CFW = 1; 1.520134 against 1.520411 for CFW = 2).
- **Sediment diagenesis: integer kind of the released-bubble count** (`Diagenesis Bubbles Code 01.f90:183`). The port replaced Intel's `KIDINT`, which returns an 8-byte integer, with a 4-byte `INT`; the target `MFTBubbReleased` is `INTEGER(8)` (`w2modules.F90:845`). Now `INT(NbubbLost, KIND = 8)`.
- **Status file written once per second** (`status_output.f90:241-272`, `w2_4_unix.f90:1666-1667`). `w2_status.json` was opened, rewritten (about 60 lines) and closed at every time step. It is now written after the first step and then at most once per second of wall-clock time; the end-of-run record is still written at the end, now also when the run fails. The layout of both records is unchanged. The `progress_percent` field of the end-of-run record, previously always 100.0, now gives the share of the simulation period reached (`status_output.f90:298-316`).
- **Iteration count printed in full** (`screen_output_unix.f90:31-32`). NIT and NV were printed with I6 and showed "******" after 999,999 iterations; they now use I0.
- **Algal vertical migration: initial value of `iday`** (`water-quality.f90:105-111`). `iday`, the Julian day of the last algal-rate update, is compared with the current day at every KINETIC_RATES call (`water-quality.f90:663`) but was first assigned at the end of that call (`:936`). Fortran does not guarantee short-circuit evaluation of `ALGAE_SETTLING_EXIST .AND. jday > iday`, and the gfortran build evaluated the comparison although migration was off, so the first call read an undefined value: a checking build with signalling-NaN initialization of local reals trapped there at JDAY 130. The variable already has the SAVE attribute (bare SAVE at `water-quality.f90:55`); it now starts at `-HUGE(iday)` in the KINETICS initialization, so the first update counts as update 1 whatever the start day. Algal migration (AVERTM) is off in the verification models.

## Build

Build with `make` in `src/` (serially; `make -j` is not supported because the Makefile declares module dependencies only on `w2modules.F90`, and a parallel build can compile a file before the module it uses). The flags are those of the v2026.02 Makefile, plus static linking of the runtime:

```
-O2 -ffree-form -ffree-line-length-none -fbacktrace -fall-intrinsics -fno-align-commons -cpp
-fdefault-real-8 -fdefault-double-8 -fmax-stack-var-size=0
-g -finit-local-zero -fcheck=all -fcheck=bounds
link: -static-libgfortran -static-libgcc -static-libquadmath
```

The `-g -finit-local-zero -fcheck=all -fcheck=bounds` group is labeled DEBUG_FLAGS but is part of the release configuration and stays on. Besides stopping a run at an out-of-bounds index, `-fcheck=all` changes the floating-point code that gfortran 16.2 generates, so removing it changes results at round-off level from the first output time, and some models are sensitive to that: a v2026.10 build without `-fcheck=all -fcheck=bounds` gave different results from the first output time of the 2001 Walter model, and a v2026.02 build with `-O2 -fmax-stack-var-size=0 -finit-local-zero` and the required flags but without `-g -fbacktrace -fcheck=all -fcheck=bounds` stops on the unmodified 2003 Walter model at JDAY 153.376 (unstable water surface in the river reach), which the full flag set passes. The checks roughly double the run time.

## Verification

Verified on 2026-10-09 with GNU Fortran 16.2.0 (Homebrew) on macOS (Apple Silicon), using the F.E. Walter Reservoir models (CE-QUAL-W2 v4.5, two waterbodies: reservoir and Lehigh River): the 2001 model over its full period (JDAY 130 to 310) and the 2003 model to JDAY 150. Three executables ran the same inputs: the v2026.02-era production binary (built February 2026 with an earlier GCC, dynamic runtime), v2026.02 rebuilt with GCC 16.2 and the same flags, and v2026.10. Outputs were compared at every output time: TSR and SPR files as written, and the W2L snapshots, which hold the water-surface elevation and U, W, temperature and every constituent of every cell every 0.125 day.

| Comparison | 2001, JDAY 130 to 310 | 2003, JDAY 130 to 150 |
|---|---|---|
| Production vs v2026.02 rebuilt (compiler version) | identical: 10 TSR and 2 SPR files byte-identical, all 1,441 W2L snapshots identical, flux files identical | identical: same files, all 161 W2L snapshots |
| v2026.02 rebuilt vs v2026.10 (the changes) | state identical as above; flux files differ (kinetic-flux correction) | same |
| v2026.10 vs v2026.10 built with `FPE_TRAP=1` | no trap; all outputs identical | no trap; all outputs identical |

Other outputs that differ between v2026.02 and v2026.10 are `W2CodeCompilerVersion.opt`, `w2_status.json` and the console log. W2L and CPL files always differ in their "Model run at" time stamp.

| Change | Test | Result |
|---|---|---|
| Failure reporting | 2003 case with changed inflow alkalinity, which stops at JDAY 153.3758 with "Unstable water surface elevation" | Production binary: exit status 0, "Simulation completed.", status file "running". v2026.10: exit status 1, error day, message and `w2.err` text on the console, one line on stderr, status "failed" with final day 153.3758; `w2.err` identical to the production binary's |
| Failure reporting | run in a folder without a control file | production binary exit status 0; v2026.10 exit status 1 |
| Kinetic-flux correction | DOSOD in `kflux_wb1.csv` against an independent sum of SOD x SODTRM(T) x DO switch x sediment area over all reservoir cells, from the W2L snapshots | 2001, 12 intervals of 14 days with 0 to 18 layer additions: v2026.10 1.010 to 1.024 times the independent value in every interval, v2026.02 1.011 to 1.677, increasing with the number of layer additions. 2003, JDAY 130 to 144: 1.015 (v2026.02 1.073). The 2001 interval without layer additions (JDAY 228 to 242) is unchanged in every flux term |
| Static runtime | `otool -L`; state comparison with the dynamically linked rebuild | only `libSystem.B.dylib`; results identical |
| `FPE_TRAP=1` | 2001 full period and 2003 to JDAY 150 under lldb | no invalid operation, division by zero or overflow |
| Status file | write rate, layout, system CPU | about one write per second (one per time step before); same layout; system CPU of the 2001 run 36.5 s against 620.9 s (v2026.02 rebuilt) |
| `iday` initial value | build with `-O1 -fcheck=all -ffpe-trap=invalid,zero,overflow -finit-real=snan`, 2003 JDAY 130 to 131 | no trap; a checking build of v2026.02 (`-O0`, same checks) traps at the first kinetics call, JDAY 130 |
| Release flags | v2026.10 with and without `-fcheck=all -fcheck=bounds`, 2001 JDAY 130 to 140 | results differ from the first W2L snapshot (0.001 deg C and 0.001 mg/L DO by JDAY 140); 2.1 times the CPU time with the checks |

The BCONV and bubble-count changes are on code paths these models do not use (CFW = 2; sediment diagenesis off), as is the algal-migration code (AVERTM off). Because the checking flags change round-off, the 2003 model, which is sensitive to round-off near JDAY 153.38, is compared to JDAY 150 only.
